# تشغيل ميزان — حالة الإنتاج ودليل استقبال جهة جديدة

هذا الملف يقول أين وصل النشر فعلًا، وما تحقّق بالاختبار لا بالافتراض، وكيف تُستقبل
جهة جديدة. لبناء نشرٍ من الصفر انظر `DEPLOYMENT.md`.

## ١) البنية القائمة

| العنصر | القيمة |
|---|---|
| المنصّة | Google Cloud Run، خدمة `mizan`، منطقة `me-central1` |
| البناء | `cloudbuild.yaml` — صورة `Dockerfile`، ثم نشر |
| الأسرار | Secret Manager، تُربط بـ`--update-secrets` |
| الحالة الباقية | حاوية Cloud Storage مركّبة بـ`gcsfuse` على `/mnt/state` |
| سلطة النزاهة | حاوية منفصلة على `/mnt/authority` |
| النطاق | Cloudflare أمام Cloud Run |

**لماذا حاويتان لا واحدة:** سجل سلطة النزاهة لا يُعدَّل بطبعه، وبقية الحالة متغيّرة.
خلطهما يجعل خطأ في إحداهما يمسّ الأخرى.

## ٢) النطاق: لماذا يلزم Worker

Cloud Run يوجّه بحسب اسم المضيف، **ولا يدعم النطاقات بنمط `*` إطلاقًا**. فسجل `CNAME`
وحده يعطي `404`. الحلّ Worker في Cloudflare يجلب من عنوان `run.app` ويمرّر المضيف
الأصلي في `x-forwarded-host` — والخادم يقرأ هذه الترويسة **قبل** `host`، فتُحلّ الجهة
من نطاقها الحقيقي لا من `run.app`.

- سجل `CNAME` باسم `*` إلى عنوان `run.app`، **مُمرَّر عبر Cloudflare** (السحابة البرتقالية).
- مسار الـWorker على `*.<النطاق>/*` فقط. **لا يُضاف الجذر** إن كان يخدم موقعًا آخر.
- وضع `Fail open`: المسار نمطي يغطي كل الجهات، فتعطُّل الـWorker يجب ألّا يُسقطها كلها.
  والـWorker موجِّه لا حارس — الحماية في الخادم: مفتاح المؤسسات والمصادقة.
- السجلات الصريحة تسبق النجمة، فالمواقع القائمة تحت النطاق لا تتأثر. والأسماء
  الرمادية (غير المُمرَّرة) لا يعمل عليها Worker أصلًا.

**الشهادة المجانية تغطي مستوى واحدًا:** `a.example.com` نعم، `a.mizan.example.com` لا.
فتكون الجهات مباشرة تحت الجذر.

## ٣) استقبال جهة جديدة — «الفيلكاوي» مثالًا

لا نشر، ولا لمس لمزوّد النطاق، ولا تعديل بيئة. طلب واحد:

```bash
KEY=$(gcloud secrets versions access latest --secret=MIZAN_ENTERPRISE_API_KEY)

curl -s -X POST https://<أي-مضيف-يعمل>/api/enterprise/tenants \
  -H "x-mizan-api-key: $KEY" -H 'content-type: application/json' \
  -d '{"orgId":"alfailakawi","subdomain":"alfailakawi","displayNameArabic":"الفيلكاوي"}'
```

تصير الجهة على `alfailakawi.<النطاق>` **فورًا**. سجل `*` يغطّيها، فلا عمل على DNS.

ثم تحقّق:

```bash
curl -s https://alfailakawi.<النطاق>/api/public/tenant
```

**ثم يبقى ما يخصّ الجهة نفسها لا البنية:** حساباتها وأدوارها من حوكمة الهوية، وسياسة
مسابقتها، ولائحة التحكيم.

### إن أرادت نطاقها الخاص

```bash
curl -s -X PATCH https://<مضيف>/api/enterprise/tenants/alfailakawi \
  -H "x-mizan-api-key: $KEY" -H 'content-type: application/json' \
  -d '{"customDomains":["quran.alfailakawi.org"]}'
```

وتوجّه الجهة نطاقها إلينا بسجل `CNAME`. النطاق الخاص يُقدَّم على الفرعي: الجهة التي
طلبت نطاقها تتوقعه هو الحاكم.

### وقف جهة

```bash
curl -s -X POST https://<مضيف>/api/enterprise/tenants/alfailakawi/suspend -H "x-mizan-api-key: $KEY"
```

**الجهة تُوقَف ولا تُحذف.** الحذف يفتح نطاقها لجهة أخرى فترث بيانات لا تخصّها.

## ٤) ثلاثة لا تفعلها

1. **لا تستبدل `MIZAN_QUESTION_ESCROW_MASTER_KEY` بعد أول مسابقة** — كبسولات الأسئلة
   معمّاة به، واستبداله يجعلها غير قابلة للفك. ولا بد أن يكون **٣٢ بايتًا بالضبط**:
   `openssl rand -hex 32` (مفتاح أطول يُرفض بـ`ESCROW_MASTER_KEY_MUST_BE_32_BYTES`).
2. **لا تستبدل `MIZAN_TRUST_SIGNING_PRIVATE_KEY_PEM`** — تبطل كل التواقيع السابقة.
3. **لا ترفع `--max-instances=1`** — المخازن الملفية (الجهات، التدقيق) تفترض كاتبًا
   واحدًا؛ نسخ متوازية على `gcsfuse` قد تُفقد سجلًا. نسخة واحدة تكفي مسابقة كاملة،
   ومتى لزمت سعة أكبر فالحل نقل هذه المخازن إلى Firestore لا رفع العدد.

## ٥) `/api/health` هو المرجع

يقول بالضبط ما هو مهيّأ. الحالة القائمة **١٢ خدمة مفعّلة**، ويبقى:

- `quranAlignmentShadowConfigured: false` — محرّك محاذاة خارجي، ميزة ظلّ لا يلزمها
  تشغيل مسابقة.
- `aiCriticalPath: false` — **صحيح ومقصود**: الذكاء الاصطناعي ليس في المسار الحرج أبدًا.

## ٦) ما يبقى قبل أول مسابقة حقيقية

1. **اعتماد المصدر القرآني** عبر «الإدارة العلمية». بوابة الجاهزية تبقى حمراء بلا مصدر
   معتمد وهذا مقصود. والاعتماد لا يُمنح بالصفة بل بالبيانات: بصمة حزمة مطابقة، و١١٤
   سورة بأعداد آياتها، وموافقات مراجعين متمايزين بالعدد الذي تُقرّه الجهة.
2. **تهيئة أول مالك — قبل تفعيل المصادقة، لا بعدها.**

   الأدوار تأتي من حوكمة الهوية لا من مزوّد المصادقة: حساب موثَّق بلا سجل هناك يُردّ
   بـ`ACCOUNT_NOT_PROVISIONED`. وإنشاء أول دعوة يتطلب `super_admin`، فأول مالك لا
   يستطيع إنشاء نفسه من الواجهة. تفعيلُ المصادقة قبل التهيئة يُقفل الباب على الجميع.

   أنشئ الحساب في مزوّد المصادقة، خذ معرّفه (UID)، ثم على مجلد الهوية نفسه الذي
   يقرأ منه الخادم:

   ```bash
   node scripts/bootstrap-owner.mjs --dir <MIZAN_IDENTITY_GOVERNANCE_DIR> \
     --uid <UID> --email <البريد> --name <الاسم> --org <معرّف الجهة>
   ```

   تعمل على سجل فارغ وحده: سجلّ فيه حساب واحد يُرفض، فلا تصير بابًا لترقية دور لاحقًا.

   والأدوار الحسّاسة تتطلب عاملًا ثانيًا (`MIZAN_REQUIRE_MFA_FOR_SENSITIVE`)، فإما
   تفعيل التحقق بخطوتين على الحساب، وإما تعطيل الاشتراط مؤقتًا، وإلا رُدّ الدخول
   بـ`MFA_REQUIRED`.

3. **وضع الإنتاج** — بعد الاعتماد والتهيئة، لا قبلهما:
   ```bash
   gcloud builds submit --config cloudbuild.yaml --substitutions _VITE_REQUIRE_AUTH=true
   ```
   يُفرّغ بيانات العرض، ويُلزم المصادقة، **وتسري بوابة الميكروفون فعليًا**: لا يُكشف
   الموضع القرآني قبل التقاط صوت حقيقي، فلا تضيع تلاوة بلا تسجيل.
4. **مراجعة بوابة الجاهزية** حتى تخلو من الموانع. هي القائمة النهائية وتقول ما ينقص
   بالعربية: عدد المحكمين، توفّر لجنة، جهاز البوابة، سياسة ظهور النتائج، مسار الصوت.
